# 架构设计回答

每个模块只选一道。以下是设计提案；只有明确标注“本项目”的部分已经实现。

## 模块一 · 第 2 题：200 轮后如何压缩

先按 token 预算决定保留什么，不按轮数机械截断。system 规则、当前目标、最近完整轮次、正在进行的工具调用链优先保留；长工具结果用结构化摘要和可回读引用代替。工具调用和结果必须成组处理，不能只留下孤立的 tool message。

较早历史压成“事实 / 用户约束 / 已完成工作 / 未完成问题 / 关键引用”几个字段，每条保留来源消息 ID。新摘要在旧摘要上增量更新，事实冲突按时间和来源处理，不让模型把猜测写成事实。原始消息仍落库。涉及金额、待办完成情况等业务状态，重新查业务表，摘要不是权威来源。

压缩后用同一组追问做回归：名字、原始约束、刚才的计算结果、未完成任务、工具失败后的纠正。检查召回正确率、重复工具率和压缩前后的 token/延迟。答不出时按来源回读或追问，避免编造连续性。摘要也会增长，需要分层或检索，而非无限拼接。

**本项目**只做字符预算下的完整旧轮次摘录，原始消息保留。优势是成本低、确定性、容易测试；缺点是摘要可能丢掉中段事实，也没有来源回读工具或精确 tokenizer，不能宣称任意细节无损。

## 模块二 · 第 1 题：半个月前的问题如何召回

先分清“再次问同一问题”与“要找上次答案”。如果用户问“上次怎么说的”，优先找历史对话；如果再次问天气或价格，即使命中历史，也要取新数据。用户改过偏好时，以最近明确表达为准。

每次新用户轮先构造检索 query：当前问题、必要的最近指代、用户 ID 和可访问范围。对历史事件做关键词与语义混合召回，再按相关性、时间、来源可靠度重排。只注入少量命中片段，附日期和来源，放入独立的参考数据区；不把历史内容升级为 system 指令。与问题无关的画像不塞入上下文，跨 session 召回需产品允许且经过用户范围过滤。

低置信度时说“我找到上次关于 X 的记录，你指的是这次吗”；涉及外部变化的答案重新查询。写 memory 时区分原话、归纳与推测，支持更正和删除，避免错误反复被当成事实。

用近似问法、同名不同用户、旧偏好被修改、重复问题但答案已过时四类样本验证。**本项目**仅做 session 内历史加载和待办读取，不实现半个月尺度的跨会话语义检索；这样保持范围清楚，也避免为了笔试引入一套向量系统。

## 模块三 · 第 1 题：长程任务如何避免忘记目标

把目标、验收条件和约束写成持久任务记录，每次执行步开始时重新读取；任务状态包含已完成证据、下一步和阻塞项。目标由用户更新，执行模型不能因为遇到困难就改写验收条件。

我会先选单执行器加检查点：每完成一个有意义的步骤保存结果引用和进度，下轮只注入目标、当前子任务和必要证据。每隔若干步或失败后检查当前动作是否仍服务目标；用步数、时间与预算上限阻止空转，遇到依赖缺失再问用户。完成判断依赖可验证结果，例如测试通过且产物存在，不能只看模型说“完成”。

方案取舍：反复注入目标简单，但多花 token；外部任务表有恢复能力，但要处理状态一致性；计划加执行分离可减少跑偏，但计划可能过时，必须允许有证据地重规划；多执行器能并行，但引入共享状态冲突和协调成本，小任务不划算。

**本项目**只保留用户输入、最近调用链、历史摘录与最大执行步数。没有持久 task 目标表，因此不把它包装成长程自动执行系统。后续最先补验收条件和检查点，而不是直接加更多角色。

## 模块四 · 第 2 题：busy 时收到用户消息或异步完成事件

让每个 session 有一个串行消费者，输入是持久事件队列。用户消息和工具完成事件先落库，带 event_id 去重，再由消费者处理。session state 只有这个消费者写，异步 worker 只能提交完成事件，不能直接把结果插进当前消息数组。

普通用户消息进入队列；“停止/取消”走优先控制通道，设置取消标志，在当前安全边界中止。是否立刻调整当前任务还是等当前轮结束，需要明确产品语义。已发生的外部副作用不能因为取消就当成没发生。补充约束可在下一个模型调用前并入，且保留它到达的顺序。

工具完成事件带 session_id、run_id、call_id 和任务版本：属于当前运行则回填；属于被取消或替代的旧运行则存为迟到结果，不能驱动新任务。用户离线时结果仍保存，重新连接后按事件游标补发。执行器用租约和 fencing token 防止故障接管后旧 worker 继续写；结果与业务副作用最好在同一事务提交，做不到则需要幂等键和对账。

**本项目**选择更小的同步策略：同 session busy 直接返回可重试提示，不排队、不实现异步通知。SQLite 原子租约和 owner 校验解决当前范围的并发问题。真正加入异步工具时，应补事件队列，而不是让回调线程绕过 Runtime 修改历史。

## 模块五 · 第 1 题：Claude Code 与 OpenAI-compatible 工具方式

先区分产品与协议：Claude Code 是一个完整编码 Agent；模型输出工具请求的格式来自模型 API，终端显示的工具卡片或日志只是展示层。不能据此断言 Claude Code 用普通文本调用工具，或 function calling 自动代替了 Runtime。

以 Claude 原生 Messages 与 GLM/豆包的 Chat Completions 兼容格式比较：

| 项目 | Claude 原生 Messages | OpenAI-compatible Chat Completions |
| --- | --- | --- |
| 调用 | assistant 内容块中的 `tool_use`，有 `id/name/input` | assistant 的 `tool_calls[]`，有 `id/function.name/function.arguments` |
| 参数 | `input` 为 JSON 对象 | `arguments` 通常为 JSON 字符串，需要再解码 |
| 回填 | user 内容中的 `tool_result`，通过 `tool_use_id` 关联 | `role=tool` 的消息，通过 `tool_call_id` 关联 |

Claude 内容块统一容纳文本、工具等不同内容，扩展表达自然，但适配层要处理块类型、顺序和关联规则。Chat Completions 的工具列表更容易对接已有函数分发器，生态兼容成本低，但要额外解析参数字符串，多模态和厂商扩展仍需适配。两者都可能给出多个调用；客户端工具通常都需要应用执行、校验参数、返回结果和限制循环。格式本身不保证业务权限或操作正确。

我的选择是应用内部统一成“公开说明 / ToolCall / ToolResult / Final”结构，差异放在模型适配层；业务工具不感知供应商。**本项目**只实现 Chat Completions，没有伪称兼容 Claude 原生 Messages；没有流式解析，也不保证所有供应商都接受同一个 Schema 子集。
