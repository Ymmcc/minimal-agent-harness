# AI 使用与开发迭代记录

使用 Codex 辅助开发，按实际实现与验证过程整理为以下阶段。提示内容为意图归纳，非逐字对话转录；测试结果对应实际执行记录。

## 1. 先定范围，避免把最小 Agent 做大

**提示要点：**

> 用 Python 做一个最小 Agent，不使用现成 Agent 框架。需要工具循环、独立 session、上下文管理和测试，代码保持容易理解。

先确定用 CLI 交互，SQLite 保存状态。网页界面、向量数据库和异步任务队列暂不加入。模型适配、Runtime、工具和存储分别放在少量文件中，后续可以独立验证。

这里保留两个运行入口：真实模型使用原生 function calling；离线 mock 用来演示和测试，明确标注能力范围。

## 2. 实现工具和状态，明确哪些参数不能交给模型

**提示要点：**

> 注册 calculator、search、todo 三个工具，每个都有名称、描述和参数 Schema。待办按用户和 session 隔离，模型不能通过参数切换用户。

工具表保存描述、Schema 和 handler，只把描述与 Schema 发给模型。user、session、owner 和调用 ID 由 Runtime 注入，不放进模型可填写的业务参数里。

calculator 使用 AST 白名单，限制运算类型、表达式复杂度和数值范围；search 返回明确标记的 mock 数据；todo 写入 SQLite。会话同时加入原子租约和 owner 校验，限制同一 session 的并发写入。

上下文按完整旧轮次摘录，原始消息留在数据库。选择字符预算做基础压缩，接受它是有损近似，不引入额外的摘要模型调用。

## 3. 接通循环，再验证结果是否真的回到模型

**提示要点：**

> 实现“构造上下文 → 请求模型 → 解析回复 → 执行工具 → 回填结果”的循环。没有工具调用时返回答案，达到最大步数就停止。

这一轮完成真实 HTTP 适配器、响应解析和 CLI。参数的 JSON 解码与 Schema 校验分开：坏参数作为工具失败结果回填，让模型有机会在下一步修正；模型响应异常则结束本轮并给出错误。

用 ScriptModel 指定“先计算，再把结果写入 todo”的响应序列，检查下一次模型调用是否收到上一步结果。同时检查工具 Schema 是否实际发送，而不是只看最终回答字符串。

首轮执行了 28 个测试，全部通过，覆盖会话隔离、重启追问、工具配对、循环上限、压缩、租约和中断恢复等功能。

## 4. 手动验收时排查中文乱码

先用命令行检查进程退出后的状态，而不只依赖内存中的测试对象：

1. 计算 `12*(3+4)`，得到 84。
2. 重新启动进程，使用同一 session 执行“再乘以 2”，得到 168。
3. 新增中文待办，再换一个 session 查询，结果为空。
4. 切回原 session，待办仍存在。

**现象：**当前环境捕获到的中文输出出现乱码，但数值计算和会话切换正常。

**定位思路复盘：**中文可能在输入、存储或输出环节出问题。先保持数据库与查询条件不变，只改变 Python 的输出编码，能缩小排查范围，避免同时修改数据库连接和业务代码。

**提示片段（按排查意图整理）：**

> 计算和会话恢复正常，但中文输出乱码。先保留同一个数据库，用 UTF-8 模式重跑相同查询，确认问题在哪一层，再决定是否修改代码。

**实际验证：**对同一数据库使用 `python -X utf8` 查询，中文待办正常显示。由此确认该次问题在默认输出编码与捕获环境之间，数据库中的中文没有损坏。

**处理：**运行说明统一采用 UTF-8 启动命令，未修改业务存储逻辑。

## 5. 补边界用例，发现并修复响应解析错误

**第一步：从正常路径转向输入结构检查。**

首轮 28 个测试通过后，继续扩充畸形模型响应、200 轮对话、HTTP 错误和超时用例。解析器原本已处理空 choices、截断和空内容，但还需要检查 message 自身的类型。

**提示片段（按测试意图整理）：**

> 不只测试空回答。把 message 换成数组等错误类型，检查解析器能否统一返回 ModelError；补上 200 轮和网络错误测试。

**第二步：先拿到可复现的失败。**

测试输入：

```python
{"choices": [{"finish_reason": "stop", "message": []}]}
```

单独运行解析测试，得到：

```text
AttributeError: 'list' object has no attribute 'get'
```

失败位置是 `message.get("content")`。这说明程序在读取内容前默认 message 一定是字典；异常也没有落入现有的协议错误转换分支。

**第三步：限定修改点。**

**提示片段（按修复意图整理）：**

> 已复现 message=[] 在 .get() 处失败。先验证 message 是对象，再读字段；错误继续走现有 ModelError 分支。保留这个失败用例，确认正常工具调用不受影响。

实际修复是在取出 message 后补类型检查：

```python
if not isinstance(message, dict):
    raise ValueError("message 必须是对象")
```

由已有的异常转换分支将 ValueError 转为 ModelError。这样既不把坏响应当作空答案，也不需要在 Runtime 里增加一个处理数组响应的特殊分支。

**第四步：回归并说明证据范围。**

重新执行完整测试集：

```text
Ran 31 tests in 28.507s
OK
```

扩充测试还验证了 200 轮后的近期追问、HTTP 错误正文脱敏、超时转换和禁止重定向。测试中的工具配对、参数纠正等正常路径也仍然通过。

### 并发与中断恢复的预防性检查

这些检查用于验证设计，没有把它们描述成已经发生过的线上事故：

- 两个线程同时抢占同一 session，断言只有一个成功。
- 模拟旧 owner 租约过期、新 owner 接管，检查旧 owner 不能写消息、改待办或释放新租约。
- 模拟 todo 已写入、工具结果未保存时中断，检查恢复只补未知结果，不重复新增。

这里的判断依据是数据库状态和调用 ID，而不是模型最后一句“操作成功”。同 call_id 去重只能覆盖该调用，换新 ID 重复表达同一业务动作仍有重复风险。
